# DeepSeek inscrit la recherche web à 0,75 USD par 1 000 requêtes, Cloudflare pose les bases de bandes de confiance : la couche économique de l'accès web pour LLM se formalise

## En tête — 4 points capitaux

- DeepSeek publie officiellement, le 16 octobre 2026, un tarif de 0,75 USD par 1 000 requêtes réussies pour ses APIs Search et Fetch, avec facturation effective au 1er novembre 2026 à 00:00 heure de Pékin ; les appels côté serveur passant par DeepSeek Harness, Claude Code ou Codex restent gratuits en période d'amorçage.
- Cloudflare publie le 16 octobre 2026, par la plume de Chris Tsoukaladelis, un plan de bandes de confiance (trust bands) pour les bots déjà vérifiés, calculées à partir du respect de robots.txt et des réponses HTTP 429 ; aucune date de disponibilité publique n'est fournie, l'évaluation reste interne.
- Amazon Ads Agent, nouveau nom unifié de la plateforme publicitaire d'Amazon, a été présenté à unBoxed 2026 le 29 septembre ; le composant DVA+ (Sponsored Display + Sponsored TV + programmatique) commence son déploiement fin octobre 2026.
- Barry Schwartz documente le 16 octobre 2026 une seconde vague de volatilité SERP de 24 à 48 heures, confirmée par au moins 14 trackers tiers horodatés Oct 14-16, huit jours après la clôture du September 2026 spam update.

## Info du jour — DeepSeek inscrit un prix public de 0,75 USD / 1 000 requêtes pour ses APIs Search et Fetch, Cloudflare prépare les bandes de confiance pour les bots vérifiés (pilier : Business SEO)

Deux publications simultanées du 16 octobre 2026 formalisent une couche économique et technique nouvelle pour l'accès web des LLM. Première publication, DeepSeek met en ligne sur sa page officielle de tarification ([api-docs.deepseek.com](https://api-docs.deepseek.com/quick_start/pricing)) deux nouvelles entrées, « Search API » et « Fetch API », facturées chacune à 0,75 USD par 1 000 requêtes réussies. La facturation effective, selon la page, démarre au 1er novembre 2026 à 00:00 heure de Pékin. Les appels côté serveur passant par DeepSeek Harness, Claude Code ou Codex ne sont pas facturés tant que la fenêtre d'amorçage reste ouverte. Deuxième publication, Cloudflare, sous la plume de l'ingénieur de recherche Chris Tsoukaladelis, pose les bases d'un système de « bandes de confiance » pour les bots déjà vérifiés, construit à partir du respect observé de robots.txt et des réponses HTTP 429. Les sources secondaires sont SessionWatcher ([sessionwatcher.com](https://sessionwatcher.com/news/deepseek-search-fetch-api-pricing-claude-code-codex-web-search), 16 octobre 2026) pour DeepSeek, et RuntimeWire ([runtimewire.com](https://runtimewire.com/article/cloudflare-verified-bots-behavior-accountability), 16 octobre 2026) pour Cloudflare, qui référence un billet du blog Cloudflare non directement récupéré ici. La page développeur Cloudflare sur les bots vérifiés ([developers.cloudflare.com](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)) détaille les deux critères d'allowlist : identification honnête et comportement non abusif, incluant le respect de robots.txt et un débit raisonnable.

Les trois mécaniques nommées par DeepSeek sont distinctes et stables. Le Search API retourne des résultats web depuis une requête texte. Le Fetch API retourne le contenu d'une URL. Les deux sont facturés par requête réussie, non par jeton. La page précise que les frais Search et Fetch sont déduits du même solde que les jetons d'inférence, et que le solde offert est consommé avant le solde rechargé. Aucun chiffre de volume moyen par appel n'est publié, ni de distribution du coût global entre jetons d'inférence et appels web dans un pipeline d'agent typique. La page ne donne pas non plus de latence cible, de couverture régionale, ni de politique de rafraîchissement de l'index sous-jacent.

Le choix de l'unité de facturation est le fait structurant. Facturer par requête réussie, et à un niveau décorrélé du nombre de jetons d'inférence consommés, découple l'économie de la recherche web de celle de la génération. Un agent qui résout une tâche en 20 recherches payera, à ce tarif, 0,015 USD de frais Search, indépendamment du modèle qui tourne derrière. Pour un LLM facturé en jetons, cette séparation rend le coût d'accès web prévisible côté marchand et comparable entre fournisseurs. SessionWatcher reprend l'annonce verbatim : « $0.75 per 1,000 successful requests » (16 octobre 2026).

Dans le même temps, le plan Cloudflare documente une bascule d'évaluation. La vérification d'identité d'un bot (allowlist) est un contrôle ponctuel. Les bandes de confiance proposent une évaluation continue à partir du comportement observé après vérification. Les signaux nommés dans le billet relayé sont deux : conformité au robots.txt et réponses aux HTTP 429 (rate limit). RuntimeWire cite le fait que Cloudflare n'a publié ni la méthode de score, ni la grille de bande, ni une procédure de validation indépendante. L'évaluation reste interne. Les bandes publiques, exposées via Cloudflare Radar ou utilisables par les clients Bot Management comme critère de politique, viendront « après évaluation interne », sans date publiée. Précédent documenté par Cloudflare : la dé-liste de Perplexity de l'allowlist de bots vérifiés pour comportement incompatible avec les préférences des éditeurs ([developers.cloudflare.com](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)).

Trois lectures opérationnelles pour un consultant qui conseille une marque ou un éditeur sur l'exposition aux moteurs IA. Première lecture, mesurabilité des coûts d'accès côté LLM. Un prix public, publié, par requête réussie permet à une marque de modéliser le coût de la découverte agentique côté fournisseur de modèle, information qui manquait jusque-là. Les comparaisons avec les concurrents (Perplexity, Google Programmable Search, Bing Web Search API) deviennent possibles à partir de barèmes homogènes. Les cabinets d'audit de visibilité IA ([[concepts/metriques-visibilite-geo]]) peuvent commencer à chiffrer l'économie de la citation (coût moyen d'une recherche multiplié par le nombre de requêtes fan-out d'une session, cf. [[concepts/agentic-search]]), pas seulement sa fréquence. Deuxième lecture, incitation à la différenciation côté marchand et éditeur. Un prix non-nul par requête web pousse chaque fournisseur de LLM à économiser les appels, donc à préférer les sources qui répondent à une requête en un seul fetch (données structurées exhaustives, Schema.org en profondeur, flux produit propre, cf. [[concepts/data-proprietaire]]). Les sites qui exigent plusieurs appels pour reconstituer une information unitaire deviennent plus coûteux à citer, et peuvent se faire préférer un concurrent plus concis. Troisième lecture, convergence avec la couche d'identification des bots. Le dispositif Cloudflare transforme la vérification d'identité en relation durable, mesurée au comportement. Un éditeur qui refuse l'accès à un bot IA via robots.txt n'a pas, jusqu'ici, de levier automatique si le bot ignore la consigne. Les bandes de confiance proposent un levier structurel : les clients Bot Management pourront théoriquement bloquer, ralentir ou laisser passer un bot selon sa bande, c'est-à-dire selon son comportement passé. Les bots vérifiés sont les premiers concernés, mais le billet Cloudflare, selon RuntimeWire, précise que le périmètre reste restreint aux acteurs déjà présents dans la BotBase.

Articulation doctrine. Les deux publications renforcent [[concepts/metriques-visibilite-geo]] par un ajout économique : le coût unitaire d'une surface d'appel web est désormais public pour un fournisseur (DeepSeek). Elles touchent aussi [[concepts/data-proprietaire]] : les flux structurés qui tiennent sur un seul appel sont de facto favorisés dans l'économie de l'inférence agentique. [[concepts/tabou-visibilite]] s'applique : la « citation » dans un LLM n'est pas un rang gratuit, c'est un appel facturé 0,75 USD / 1 000 requêtes côté fournisseur ; mesurer une visibilité sans tenir compte des contraintes de budget du fournisseur de modèle est une mesure incomplète.

Six réserves méthodologiques explicites. Premièrement, le prix DeepSeek s'applique à un fournisseur de LLM parmi plusieurs ; Perplexity, OpenAI, Google ne publient pas de barème équivalent pour leur accès web interne. L'extrapolation est à faire explicitement, pas implicitement. Deuxièmement, DeepSeek ne donne ni volumétrie moyenne de requêtes par session agentique, ni couverture d'index, ni politique de recrawl ; impossible à ce stade d'estimer le coût réel d'une résolution de tâche. Troisièmement, les appels côté serveur gratuits via Claude Code, Codex, DeepSeek Harness créent une période d'amorçage dont la fin n'est pas publiée distinctement ; la facturation nominale est au 1er novembre, le free period est encadré par une « séparation d'annonce ». Quatrièmement, Cloudflare ne publie ni la méthode de score, ni la grille des bandes, ni la validation indépendante ; la seule corroboration à ce jour est RuntimeWire, source secondaire, pas la documentation primaire Cloudflare. Cinquièmement, le périmètre Cloudflare des bandes de confiance est limité aux bots déjà vérifiés : les crawlers IA non enregistrés dans la BotBase ne sont pas concernés par ce dispositif à ce stade. Sixièmement, aucune mesure d'impact pour éditeur ni pour LLM n'est encore publiée pour ces deux annonces. Les lectures ci-dessus restent des interprétations méthodologiques, non des résultats observés.

Non résolu par cette édition : à quelle fréquence un LLM concurrent va-t-il adopter un barème similaire par requête, et dans quel délai Cloudflare publiera-t-il un référentiel public utilisable comme critère de politique côté éditeur. Prédictions ouvertes datées en fin d'édition.

## Brève 1 — Amazon Ads Agent remplace Amazon Ad Console, DVA+ se déploie à partir de fin octobre 2026 (pilier : Agentic search)

Amazon a présenté le 29 septembre 2026 à unBoxed à San Francisco une refonte de sa plateforme publicitaire. Le nouveau nom est « Amazon Ads Agent », rapporté par [Adweek](https://www.adweek.com/media/amazon-ads-agent-campaign-manager/), [Shopifreaks](https://www.shopifreaks.com/amazon-unveils-ads-agent-to-automate-media-planning-and-campaign-creation/) et [RelevantAudience](https://www.relevantaudience.com/ecommerce-marketing/amazon-ads-agent-unboxed-2026-full-funnel-dva-plus/). La plateforme remplace Amazon Ad Console et regroupe trois types de campagnes : sponsored ads, DVA+ (Sponsored Display + Sponsored TV + programmatique) et Full-Funnel Campaigns. Full-Funnel Campaigns est disponible immédiatement aux annonceurs US. DVA+ commence son déploiement fin octobre 2026. Les outils conversationnels (planification agentique, forecasts, suggestions de budget, ciblage en langage naturel, analytics en langage naturel) sont présentés comme arrivant « sur les mois à venir ». Chiffre affiché par Amazon : les annonceurs appliquant les recommandations de ciblage naturel ont vu « plus de 25 % de nouveaux clients et plus de 10 % de baisse du coût par impression » en moyenne. Donnée vendeur, pas d'audit tiers publié. Lecture SEO : Amazon continue à déplacer la découverte produit vers un orchestrateur conversationnel propre, en parallèle du commerce agentique via UCP / ACP côté Google / OpenAI. Un marchand actif sur Amazon ne mesure plus seulement sa visibilité organique sur Amazon Search, il mesure aussi sa performance face aux recommandations générées par Amazon Ads Agent. L'interaction avec Rufus et Alexa+ dans le même écosystème est détaillée par Adweek.

## Brève 2 — Seconde vague de volatilité SERP Google documentée par Barry Schwartz le 16 octobre 2026, confirmée par 14 trackers (pilier : Actualité SEO)

Barry Schwartz publie le 16 octobre 2026 à 07:51 un article ([seroundtable.com](https://seroundtable.com/google-search-ranking-volatility-chatter-42317.html)) documentant une seconde vague de volatilité SERP de 24 à 48 heures. L'article nomme trois perturbations possibles superposées : clôture tardive du September 2026 spam update (fenêtre encore ouverte à la lecture), effets persistants du poisoning anti-scraping documenté par Nozzle le 10 octobre, et possibles changements de rendering non annoncés. Les 14 trackers tiers horodatés dans l'article sont Wincher (Oct 16), CognitiveSEO (Oct 15), AWR (Oct 16), Wireboard (Oct 16, aggrégé), AccuRanker Grump (Oct 15), Serpstat (Oct 14), DataForSEO SERP Volatility (Oct 15), Mangools SERPWatcher (Oct 10), Zutrix Tension (Oct 16), SEMrush Sensor (Oct 16), Mozcast (sans date d'image), SimilarWeb (Oct 16), Sistrix (Oct 16), Algoroo (Oct 16). Les commentaires WebmasterWorld rapportent des baisses de trafic sévères sur e-commerce, news et blogs, et des stale stories dans Google News et Discover. Schwartz observe également une augmentation des actions manuelles. Google n'a pas communiqué sur cette seconde vague au moment de l'écriture. Lecture SEO : pour un éditeur ou un e-commerçant qui constate une baisse post-8 octobre, le diagnostic est à décomposer en trois causes potentielles distinctes, non en une seule attribution « spam update ». La méthodologie est : vérifier la fenêtre de clôture annoncée Google, vérifier l'exposition à des pages impactées par le poisoning (volume d'URLs non visitables par un bot classique), et vérifier les URLs servies via rendering différencié. [Confirmation croisée par la version française de la couverture SE Roundtable](https://seroundtable.com/google-search-ranking-volatility-chatter-42317.html).

## Brève 3 — Google Healthcare review snippet drop : onze jours après Schema App, aucun commentaire Google (pilier : Niche SEO)

Rappel du fait documenté le 7 octobre 2026 par Barry Schwartz ([seroundtable.com](https://seroundtable.com/google-drops-healthcare-review-snippets-42248.html)) : Google a cessé d'afficher les rich results de review pour les pages healthcare, même avec review schema correctement implémenté. La source primaire est Andrea Badder (Schema App), qui a observé une première baisse en fin mai 2026 et une seconde baisse début août 2026 pour certaines organisations. Les tests Schema App ont inclus plusieurs variantes d'implémentation (aggregateRating, chemins de propriété alternatifs, multi-typing avec Product) ; aucune n'a restauré les snippets. Confirmation secondaire par [Optimixed](https://optimixed.com/article/google-stops-showing-review-snippets-on-healthcare-pages-247b3b). Nouveau fait au 18 octobre 2026 : onze jours après la couverture, aucun commentaire officiel de Google n'est publié, ni dans Search Central, ni dans le changelog documentation ([developers.google.com/search](https://developers.google.com/search/docs/appearance/structured-data/review-snippet)). Lecture SEO : la perte d'une surface de résultat enrichi sur une verticale sensible (healthcare) sans annonce officielle est un pattern de dépréciation silencieuse déjà observé pour les FAQ (2023) et les HowTo (2024). Les éditeurs healthcare sont incités à retirer le code review schema qui n'améliore plus la position (donc n'améliore pas la citation), à conserver la donnée produit (aggregateRating) comme signal pour les moteurs de réponse générative hors Google, et à auditer leur stratégie de preuve sociale via d'autres surfaces (Google Business Profile, pages produit sans review markup, citations tierces). Chiffres historiques pour contextualiser l'enjeu : Sharp Healthcare rapportait +119 % de CTR quand review snippet était attribué, Marshfield Clinic rapportait +454 % sur URLs médecins. La perte de ce potentiel de CTR est significative à l'échelle d'un portefeuille national.
