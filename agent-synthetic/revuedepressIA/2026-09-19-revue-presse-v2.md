## Info du jour — Business SEO : Google Merchant Center ouvre le 18 septembre 2026 le support Merchant API pour les product reviews avec les endpoints v1alpha accounts.productreviews insert/get/list/delete, remplace la mention API isn't currently supported for product reviews data sources par Add product reviews using API et bascule l'interface de ANALYTICS Reviews vers Products & store Reviews en Merchant Center Next

Google publie le 18 septembre 2026 une révision de la documentation officielle Merchant Center [Add product reviews (support.google.com/merchants/answer/14620732)](https://support.google.com/merchants/answer/14620732?hl=en) qui ajoute la méthode API comme quatrième mode de soumission des reviews. La version archivée le 21 août 2026 sur [web.archive.org (support.google.com/merchants/answer/14620732)](https://web.archive.org/web/20260821144704/https://support.google.com/merchants/answer/14620732?hl=en) mentionnait explicitement « API isn't currently supported for product reviews data sources ». La version publiée le 18 septembre 2026 remplace ce texte par « Add product reviews using API. Automatically upload and manage product reviews data using Google's Merchant API », citation reprise verbatim par [Search Engine Roundtable Barry Schwartz : Google Merchant Center API Supports Product Reviews (seroundtable.com/42101)](https://www.seroundtable.com/google-merchant-center-api-supports-product-reviews-42101.html) publié le même jour.

La documentation développeur associée [Review products using Merchant API (developers.google.com/merchant/api/guides/reviews/products)](https://developers.google.com/merchant/api/guides/reviews/products) expose quatre méthodes REST sur le domaine `merchantapi.googleapis.com/reviews/v1alpha`. La méthode `accounts.productreviews.insert` (verbe HTTP POST sur `accounts/{ACCOUNT_ID}/productReviews:insert`) crée ou met à jour une product review, prend en entrée un paramètre `datasource.name` et une ressource `productreview`. La documentation précise textuellement « This request overwrites the entire product review resource, so the request needs to include all the details to avoid losing information » : chaque insert écrase la ressource complète, aucune fusion partielle n'est appliquée. La méthode `accounts.productreviews.get` (GET sur `accounts/{ACCOUNT_ID}/productReviews/*`) est en lecture seule. La méthode `productreviews.list` (GET sur `accounts/{ACCOUNT_ID}/productReviews`) permet le listing paginé de toutes les reviews créées. La méthode `accounts.productreviews.delete` (DELETE sur `accounts/{ACCOUNT_ID}/productReviews/*`) supprime une review unitairement. Des exemples de code Java sont publiés pour l'insertion asynchrone de plusieurs reviews, la récupération, le listing avec pagination et la suppression.

Le chemin d'accès à la fonctionnalité dans l'interface Merchant Center bascule simultanément. L'ancien chemin ANALYTICS > Reviews > Product reviews (Merchant Center legacy) est remplacé par Products & store > Reviews > Product reviews > Manage product review sources (Merchant Center Next), selon la mise à jour Google reprise par [Search Engine Roundtable Barry Schwartz](https://www.seroundtable.com/google-merchant-center-api-supports-product-reviews-42101.html). Le terme « feed submission » utilisé dans l'ancienne documentation est remplacé par « data source submission » dans la nouvelle. Le processus d'onboarding est également clarifié : après soumission du formulaire d'intérêt, un agent Google doit examiner manuellement la demande et activer le compte avant l'ouverture des soumissions programmatiques.

La documentation Merchant Center liste désormais quatre méthodes de soumission des reviews. Premièrement, Scheduled Fetch (Google fetche un fichier XML hébergé à une URL selon un planning configuré). Deuxièmement, SFTP ou Google Cloud Storage (upload via credentials activés sur le compte). Troisièmement, upload direct depuis un poste. Quatrièmement, l'API Merchant nouvellement supportée. Les exigences opérationnelles restent inchangées : chaque data source doit être mise à jour au moins une fois par mois, le fichier XML validé doit peser moins de 4 Go, le format compressé zip est accepté avec au maximum 5000 fichiers par archive.

Trois lectures opérationnelles pour un consultant SEO qui accompagne un marchand e-commerce à fin septembre 2026. La première : l'ouverture de l'API sur les reviews rend automatisable une chaîne qui reposait jusqu'ici sur des envois de fichiers manuels ou programmés, avec un coût de maintenance différent (un cron qui pousse via l'API a un profil d'échec technique distinct d'un cron qui uploade un fichier sur SFTP ou d'un fetch planifié). Un audit Merchant Center peut désormais recommander une bascule sur l'API pour les catalogues qui exigent une mise à jour plus fréquente qu'une fois par mois (par exemple, un catalogue avec un turnover de reviews élevé, ou un catalogue avec un flux d'avis provenant d'un moteur de collecte tiers en temps réel). La deuxième : chaque insert écrase la ressource complète selon la documentation officielle, ce qui contraint l'architecture d'ingest tierce (l'intégrateur doit garantir la présence de tous les champs à chaque appel, sinon les champs omis sont effacés). Le mode de mise à jour partielle n'est pas exposé publiquement dans la documentation actuelle. La troisième : la structure Merchant Center Next (Products & store > Reviews) devient la seule interface documentée, ce qui accélère la fin de support de Merchant Center legacy pour les tâches de gestion des reviews.

L'articulation à la doctrine du vault se joue sur trois concepts distincts. Le premier ancrage est [[concepts/arbitrage-plateforme-publication]] : Google contrôle simultanément la primitive de collecte (Merchant Center via API ou fichier), la primitive d'affichage (Product Rich Results, AI Overviews Shopping, Google Shopping Ads, badges de qualité), et la primitive de qualité (approbations de contenu, disapproval sur violation de politique, seuils qualité entité). L'ouverture de l'API rend automatisable le point de collecte sans modifier l'asymétrie sur les points d'affichage et de qualité : le marchand pousse plus facilement, mais les critères de sélection restent opaques. Le deuxième ancrage est [[concepts/metriques-visibilite-geo]] : la baseline pré-18 septembre 2026 des reviews soumises par SFTP ou fetch pour un catalogue donné reste un référent traçable ; les indicateurs post-18 septembre 2026 doivent isoler la fraction de reviews soumises par API pour mesurer la variation d'impact sur les surfaces d'affichage (fréquence d'affichage des rich snippets produit, présence dans Google Shopping AI Overviews, présence dans les Product Knowledge Panels). Cet instrumentage n'est pas fourni nativement par Merchant Center côté marchand : un consultant qui recommande la bascule doit prévoir des jalons de mesure externes. Le troisième ancrage est [[concepts/tabou-visibilite]] : la « visibilité produit AI » ne se réduit plus à la position dans Google Shopping mais recouvre plusieurs surfaces distinctes (rich snippets classiques sur SERP, Product Knowledge Panels, AI Overviews Shopping, Google Shopping Ads gratuits ou payants, agents conversationnels dérivés). La mesure de succès devient la conversion mesurée par surface, ce qui exige un tag produit distinct par chemin d'affichage, encore imparfaitement standardisé à date.

Quatre réserves méthodologiques à noter. Premièrement, le passage à la disponibilité de l'API dans la documentation ne dit rien sur le taux d'adoption effectif ni sur le calendrier de dépréciation des trois autres méthodes de soumission ; le SFTP, le fetch planifié et l'upload direct restent listés et fonctionnels selon la documentation actuelle. Un consultant qui migre un client vers l'API doit anticiper une phase de bascule échelonnée et documenter la coexistence des deux chaînes pendant plusieurs semaines. Deuxièmement, la version v1alpha exposée pour Reviews indique un statut préliminaire ; les endpoints, les signatures et le comportement d'écrasement complet peuvent évoluer sans préavis. Les intégrations construites contre v1alpha exposent le marchand à des breaking changes non préannoncés. Troisièmement, la documentation développeur ne publie pas les seuils d'éligibilité programme Product Reviews par verticale ni les critères de disapproval agrégés post-migration ; un marchand qui bascule sur l'API sans disposer de ces seuils opère à l'aveugle sur ses critères de qualité. Quatrièmement, l'ouverture de l'API concerne exclusivement les product reviews au sens Merchant Center et ne couvre pas les seller reviews (revues de vendeur, autre programme Google) ni les reviews issues d'un module UGC on-site pour lequel Google publie séparément des recommandations JSON-LD Review markup ; l'API Merchant n'unifie pas ces trois flux distincts.

Trois prédictions vérifiables datées avec critères binaires. **P-2026-09-19-v2-1** au 31 mars 2027, Google aura publié une version stable (v1, sans suffixe alpha ou beta) de l'API Reviews pour les product reviews au sens Merchant Center avec un `Latest updates` sur [developers.google.com/merchant/api/latest-updates](https://developers.google.com/merchant/api/latest-updates) documentant explicitement la promotion de v1alpha vers v1, OU la v1alpha aura été retirée avec redirection vers un autre versionnage. Confiance 0,45. **P-2026-09-19-v2-2** au 30 juin 2027, au moins une plateforme tierce de collecte de reviews client à échelle (Trustpilot, Avis Vérifiés, Feefo, Reviews.io, Bazaarvoice, Yotpo, Judge.me ou équivalent) aura publié en son nom propre un guide d'intégration nommant explicitement `accounts.productreviews.insert` sur `merchantapi.googleapis.com/reviews/v1alpha` avec exemples de code, ce qui témoignerait d'une adoption écosystème plutôt qu'une capacité isolée. Confiance 0,55. **P-2026-09-19-v2-3** au 31 décembre 2026, un cabinet non-Google (Datadog e-commerce, ChannelAdvisor, Feedvisor, WordStream ou équivalent) aura publié une mesure agrégée sur un parc distinct d'au moins 200 marchands documentant la fraction de product reviews soumises par API vs SFTP vs fetch vs upload direct dans les six semaines suivant le 18 septembre 2026. Confiance 0,25.

## Brève 1 — Actualité SEO : Google exige le 18 septembre 2026 le marquage des produits adultes dans les feeds Merchant Center via l'attribut adult ou dans le markup structuré via hasAdultConsideration, avec un périmètre limité aux fonctionnalités Google Shopping et sans impact sur la visibilité en résultats web organiques classiques

[Search Engine Roundtable Barry Schwartz : Google Now Requires You Label Adult Products In Ecommerce Feeds (seroundtable.com/42116)](https://www.seroundtable.com/google-adult-products-labels-42116.html) publié le 18 septembre 2026 documente que Google a mis à jour ses règles de contenu explicite pour exiger le marquage des produits adultes sur deux canaux techniques distincts. Le premier canal est le feed Merchant Center via l'attribut `adult` (documentation Google Shopping). Le second canal est le markup structuré via l'annotation `hasAdultConsideration` (documentation Google Search Central structured data). La citation reprise par Barry Schwartz est verbatim : « label adult products in ecommerce feeds or markup. If you're optimizing your product listings to appear in Google Shopping features and your products are considered adult-oriented according to Google's adult-oriented content policy, label them in your Merchant Center feeds with the adult attribute ». Le périmètre de l'exigence est explicitement limité aux fonctionnalités Google Shopping, avec une clause additionnelle citée dans l'article : le marquage « doesn't affect your site's visibility in organic web search results ». Aucune date d'entrée en vigueur exécutive n'est publiée dans le texte de la mise à jour.

Lecture opérationnelle pour un consultant SEO qui accompagne un marchand e-commerce dont le catalogue contient des produits classés adultes en septembre 2026. Le double canal de marquage (feed OR markup) exige un audit de conformité qui vérifie la présence effective de l'attribut sur les deux surfaces si le marchand utilise à la fois Merchant Center et markup structuré JSON-LD ; une divergence entre les deux surfaces (produit adulte marqué en feed mais non marqué en JSON-LD, ou l'inverse) génère un risque d'inconsistance de signal côté Google. Le marquage n'affecte pas la position organique classique selon Google, ce qui limite l'impact SEO strict, mais il conditionne l'éligibilité aux surfaces Shopping (Free product listings résiduels, Google Shopping Ads, Shopping graph). Cet ancrage recoupe [[concepts/arbitrage-plateforme-publication]] : Google unifie la primitive de marquage adulte sur deux canaux techniques distincts (feed Merchant Center + Search Central structured data) sans détailler nominativement la table de correspondance des catégories couvertes ni le seuil quantitatif de contenu adulte qui déclenche l'exigence de marquage.

Deux réserves méthodologiques. Premièrement, l'absence de date d'entrée en vigueur publiée interdit d'anticiper le calendrier d'application des sanctions ou de disapproval de produits non marqués ; la lecture prudente est de considérer le marquage comme requis dès la publication de la mise à jour documentaire. Deuxièmement, la définition opérationnelle des « produits considérés adultes selon la politique Google » n'est pas détaillée dans le texte de la mise à jour reprise par Barry Schwartz ; un catalogue avec des cas frontière (lingerie, produits de beauté sensuels, produits de soins intimes, livres à contenu adulte) doit consulter séparément la [documentation politique de contenu adulte Google Ads et Merchant Center](https://support.google.com/adspolicy/answer/6023699) pour identifier ses produits éligibles.

## Brève 2 — GEO / search IA : Cheers publie une mesure baseline home services sur 28 jours clôturée le 2 septembre 2026 documentant 356 019 citations réparties sur 32 requêtes et 100 aires métropolitaines US-Canada, avec Gemini 80,7 pct citations sur site prestataire direct contre ChatGPT 48,8 pct site prestataire et 44,7 pct annuaires et plateformes d'avis

[Cheers.tech Dylan Allen-Arnegård : ChatGPT, Gemini, Perplexity Sources for Local Businesses (cheers.tech/geo-academy/ai-search-engine-source-differences)](https://www.cheers.tech/geo-academy/ai-search-engine-source-differences) publie une mesure de baseline sur 28 jours clôturée le 2 septembre 2026 (publication initiale mars 2026, mise à jour et vérifiée septembre 2026). Le protocole documenté sur la page : 32 requêtes home services en langage naturel, 100 aires métropolitaines couvrant US et Canada, quatre moteurs testés (ChatGPT, Perplexity, Google AI Overviews/AI Mode, Gemini), 356 019 citations agrégées cumulées sur la période, données agrégées sans nommer clients. La répartition des citations vers le site du prestataire direct : Gemini 80,7 pct, Perplexity 72,3 pct, Google AI Overviews et AI Mode 70,3 pct, ChatGPT 48,8 pct. La répartition des citations vers annuaires et plateformes d'avis : ChatGPT 44,7 pct, Google AI Overviews 11,4 pct spécifiquement sur google.com. Les cinq domaines plateforme les plus cités toutes aires cumulées sont google.com, expertise.com, angi.com, bbb.org, reddit.com. Verbatim Cheers : « One strategy does not cover three engines. Gemini rewarded the owned site, ChatGPT rewarded third-party and directory pages, Perplexity rewarded vertical sources ».

Lecture opérationnelle pour un consultant SEO qui accompagne un prestataire home services US ou Canada en septembre 2026 (plombier, électricien, HVAC, entreprise de rénovation, jardinage). L'écart mesuré Gemini 80,7 pct vs ChatGPT 48,8 pct sur les citations dirigées vers le site propre du prestataire signifie qu'une stratégie fondée sur la qualité de la page prestataire elle-même (pages de services locales détaillées, coordonnées vérifiables, horaires, tarifs indicatifs, zones d'intervention, témoignages sur site) est différentiellement récompensée selon le moteur : forte sur Gemini, moyenne sur ChatGPT qui cite pour moitié des annuaires tiers et plateformes d'avis (Angi, BBB, Reddit, Expertise.com). Un consultant qui accompagne un prestataire doit donc décomposer son objectif de visibilité par moteur, avec deux chaînes de travail distinctes : renforcement de la page prestataire pour Gemini (couverture Perplexity 72,3 pct et Google AI Overviews 70,3 pct proche), et présence dans les annuaires tiers pour ChatGPT (Angi, BBB, Yelp, plateformes verticales). Un tag distinct de source d'origine sur les leads permet de mesurer la conversion par moteur, encore imparfaitement disponible dans les CRM standards. Cet ancrage recoupe [[concepts/metriques-visibilite-geo]] : la baseline Cheers du 2 septembre 2026 sur 356 019 citations est un référent daté qui permet de contextualiser la position d'un site prestataire spécifique dans la distribution ; la mesure locale sur un client donné (fréquence de citation sur ses propres requêtes cibles) doit être rapportée à cette baseline sectorielle pour être interprétée.

Trois réserves méthodologiques. Premièrement, l'étude Cheers est publiée par un vendeur de plateforme de visibilité locale (Cheers, société YC 2024, San Francisco, Dylan Allen-Arnegård CEO co-fondateur) qui a un intérêt commercial à démontrer l'existence d'un écart mesurable entre moteurs justifiant l'usage de sa plateforme ; les chiffres sont autoreportés à partir d'un panel d'entreprises clientes ou observées, sans reproduction indépendante par un cabinet non-vendeur à ce jour, ce qui limite la portée quantitative comme référent absolu. Un cabinet non-Cheers (BrightLocal, Whitespark, Sterling Sky, Moz Local ou équivalent) publiant une mesure agrégée sur un parc distinct avec méthodologie comparable serait nécessaire pour établir la robustesse de la répartition observée par moteur. Deuxièmement, le périmètre home services n'est pas défini nominativement en catégories dans la version publiée (les 32 requêtes ne sont pas listées) ; l'extrapolation à un autre vertical local (dining, beauty salons, attractions touristiques désormais couverts par les Aggregator et Supplier units EEA selon l'édition du 19 septembre matin) n'est pas justifiée. Troisièmement, la mesure porte exclusivement sur des aires métropolitaines US et Canada ; l'extrapolation à un prestataire home services EEA (Allemagne, France, Belgique, Pays-Bas, Suède, Espagne, Italie) doit intégrer que les Aggregator et Supplier units EEA introduisent une surface d'affichage distincte non couverte par la mesure Cheers, ce qui limite la validité géographique.
