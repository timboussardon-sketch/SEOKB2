## Info du jour — Recherche agentique : Perplexity retire ses endpoints Sonar Chat Completions le 27 septembre 2026 au profit de l'Agent API, impose une migration structurelle à toute la chaîne d'outils GEO tiers qui interrogent la couche recherche de Perplexity pour mesurer les citations IA, et fait glisser la logique d'appel de `pick a model` vers `configure a preset`

Le 14 août 2026, Perplexity a publié sur sa [documentation officielle](https://docs.perplexity.ai/docs/agent-api/migrate-from-sonar/overview) et sur le [forum Perplexity API Platform](https://community.perplexity.ai/t/sonar-is-moving-to-the-agent-api/5802) l'annonce du retrait de ses endpoints Sonar Chat Completions au 27 septembre 2026, avec 45 jours de délai pour la migration. La date est confirmée par [UsagePricing](https://www.usagepricing.com/blueprint/activity/perplexity-ai-2026-08-14-sonar-api-sunset), par [AI Watch Station](https://ai-watch-blog.vercel.app/en/posts/2026-08-13-perplexity-agent-api-launch/) le 13 août, par [Byteiota](https://byteiota.com/perplexity-sonar-retires-sept-27-agent-api-migration-guide/) le 25 août, par [Ecorpit](https://ecorpit.com/perplexity-sonar-retirement-september-27-agent-api-migration-2026/), et détaillée le 20 septembre 2026 par [LLM Gateway](https://llmgateway.io/blog/perplexity-sonar-api-retirement).

Un, le calendrier précis et le mécanisme technique. Perplexity Sonar est un ensemble d'endpoints Chat Completions compatibles OpenAI qui exposent la couche recherche web de Perplexity à des applications tierces depuis 2024, et servent à interroger la base de données de citations Perplexity pour construire des outils GEO tiers. Le 25 septembre 2026, le modèle `perplexity/sonar` bascule sur le transport Agent API sans changement visible pour les clients qui appellent `/v1/chat/completions`, avec la même forme de requête, le même streaming, le même schéma JSON et le même tableau `search_results` selon [LLM Gateway](https://llmgateway.io/blog/perplexity-sonar-api-retirement). Le 27 septembre 2026, les modèles `perplexity/sonar-pro`, `perplexity/sonar-reasoning-pro` et `perplexity/sonar-deep-research` deviennent non-routables : l'Agent API rejette leurs identifiants et ne propose pas de substitution automatique. Les clients qui utilisent ces trois modèles doivent migrer manuellement avant le 27 septembre, sans quoi leurs requêtes retournent des erreurs.

Deux, le mapping des modèles Sonar vers les presets Agent API. Selon la [documentation Perplexity](https://docs.perplexity.ai/docs/agent-api/migrate-from-sonar/overview) reprise par [Byteiota](https://byteiota.com/perplexity-sonar-retires-sept-27-agent-api-migration-guide/), la correspondance est la suivante : `sonar` vers le preset `fast` ou `low`, `sonar-pro` vers le preset `medium`, `sonar-reasoning-pro` vers le preset `high`, `sonar-deep-research` vers le preset `xhigh` ou `wide-research`. Chaque preset exécute un modèle sous-jacent différent, avec un comportement de recherche différent et une facturation différente. [LLM Gateway](https://llmgateway.io/blog/perplexity-sonar-api-retirement) ajoute que le passage remplace un tarif à la requête par une facturation individuelle par recherche et cite un chiffrage interne de son propre benchmark : « a grounded question measured about a third cheaper than on the old path in our own testing », avec la réserve que la variation dépend de la longueur des tokens de sortie.

Trois, la citation clé sur la doctrine de rétrocompatibilité. LLM Gateway assume publiquement l'absence de substitution silencieuse : « A model id is a contract. When we cannot honor it, an error you can see beats a substitution you cannot ». Cette position, que la documentation Perplexity valide implicitement en refusant les alias non-existants, oblige chaque client à faire un choix technique explicite, et pas une reconduction implicite. Elle exclut par construction le scénario du client qui découvre au premier bug de production que son outil interroge un modèle différent.

Quatre, l'écosystème d'outils GEO tiers concernés. La couche Sonar Chat Completions est le point d'entrée technique privilégié pour construire un outil qui mesure les citations dans les réponses Perplexity : Peec AI, Profound, tryprofound, Athena HQ, Scrunch, BrightEdge Copilot, Rankscale, Otterly, Xfunnel AI, Siftly, RankAI, ainsi que les serveurs MCP dédiés au tracking GEO (`mcp-geo` par exemple). Ces outils envoient un prompt calibré à `/v1/chat/completions` avec un modèle Sonar, récupèrent le tableau `search_results` et l'annotent pour produire les métriques de citation par domaine (part de citations, part de sources récupérées, rang de citation). La migration au 27 septembre 2026 impose à chaque éditeur de ces outils un choix technique : rester sur `perplexity/sonar` migré au transport Agent API le 25 septembre sans changement de modèle sous-jacent, ou bien basculer vers un preset Agent API supérieur (`medium`, `high`, `xhigh`), avec un comportement de recherche différent et un prix différent.

Cinq, le nouveau régime tarifaire et technique de l'Agent API. La [documentation Perplexity](https://docs.perplexity.ai/docs/agent-api/migrate-from-sonar/overview) précise que l'Agent API facture les tokens de modèle tiers au tarif direct du fournisseur sans marge, et qu'elle mesure séparément chaque appel d'outil : `web_search`, `fetch_url`, `sandbox`, `code_execution`, etc. Le [changelog Perplexity](https://docs.perplexity.ai/docs/resources/changelog) confirme que le MCP Server v1.0.0 publié en juillet 2026 a déjà migré ses outils backend `perplexity_ask` vers le preset `fast`, `perplexity_reason` vers `medium`, `perplexity_research` vers `high`. La conversion `pick a model` vers `configure a preset` structure désormais tous les appels à la couche recherche de Perplexity : le développeur ne choisit plus un modèle nommé, il configure un preset qui compose modèle et outils.

Cinq lectures opérationnelles pour un consultant SEO ou GEO. Un, si votre équipe utilise un outil GEO tiers (Peec AI, Profound, Athena HQ, Scrunch, BrightEdge Copilot, Rankscale, tryprofound, Otterly, Siftly, RankAI ou équivalent), demandez à l'éditeur avant le 27 septembre 2026 quel preset Agent API il utilisera post-migration, quelle est la variation de comportement attendue sur les mesures de citation (nombre de sources récupérées, ordre de citation, verbatim de la réponse) et quelle est la variation tarifaire répercutée. Une réponse « c'est transparent, rien ne change » est un signal faible sur la maîtrise technique de l'éditeur : la bascule modifie au moins le mécanisme d'appel, et souvent le prix. Deux, si votre équipe interroge directement `perplexity/sonar-pro` ou `perplexity/sonar-reasoning-pro` dans un script interne de monitoring GEO, l'échéance du 27 septembre est ferme et sans substitution automatique. Migrer manuellement vers le preset `medium` ou `high` avant cette date évite les erreurs de production. Trois, la mesure de citation Perplexity avant et après le 27 septembre 2026 n'est pas garantie comparable sur la période. Un consultant qui audite l'évolution de citations Perplexity d'un client doit isoler la fenêtre pré-migration (jusqu'au 27 septembre) et post-migration (à partir du 28 septembre) pour ne pas confondre une variation de citation liée au changement de moteur avec une variation liée au contenu du client. Quatre, la baisse de coût unitaire annoncée par LLM Gateway (« about a third cheaper ») est un benchmark interne d'un éditeur qui a un intérêt commercial à minimiser le coût perçu de la migration ; à traiter comme direction, pas comme mesure indépendante. Cinq, la migration Perplexity est un signal opérationnel sur le mouvement général de la couche recherche IA vers un modèle agentique (Agent API + presets + outils appelés séparément) qui est cohérent avec le mouvement documenté sur l'écosystème MCP depuis novembre 2024 : la surface d'intégration côté client se stabilise autour du triptyque `presets + outils + tarification à l'appel`, et la surface `pick a model` recule.

Trois concepts doctrine articulés. Le concept [`agentic-search`](../../wiki/concepts/agentic-search.md) reçoit une matérialisation technique : le modèle mental « choisir un modèle nommé pour interroger un moteur IA » cède la place au modèle « configurer un preset qui compose un modèle, des outils et une politique de recherche », qui est le mode d'appel natif d'un agent autonome. Un consultant GEO qui construit sa stratégie de mesure sur l'appel direct à un modèle nommé (Sonar Pro, Sonar Reasoning Pro) doit maintenant la re-fonder sur le paradigme preset, cohérent avec l'écosystème MCP dans lequel l'agent choisit lui-même l'outil et le modèle appelés. Le concept [`metriques-visibilite-geo`](../../wiki/concepts/metriques-visibilite-geo.md) reçoit un caveat méthodologique concret : les métriques `Imp_wc`, `Imp_pos` et `Subjective Impression` mesurées via Perplexity avant le 27 septembre 2026 sur `sonar-pro` ou `sonar-reasoning-pro` ne sont pas garanties comparables aux mêmes métriques mesurées après cette date sur les presets `medium` ou `high` de l'Agent API. Le consultant qui construit un dashboard de suivi de citations Perplexity doit noter la bascule comme rupture méthodologique sur son axe temporel. Le concept [`structural-information-geo`](../../wiki/concepts/structural-information-geo.md) reçoit une donnée d'infrastructure : la couche recherche des moteurs IA se re-modèle en composant `presets + outils` avec facturation séparée des appels d'outils. Un consultant qui optimise le contenu d'un site pour être récupéré par la couche `web_search` d'un agent Perplexity ou équivalent doit désormais penser en termes d'appels d'outils facturés séparément et pas en termes de position dans une liste de résultats agrégée par un modèle nommé.

Cinq réserves méthodologiques. Un, la source LLM Gateway est un éditeur d'infrastructure LLM tiers qui a un intérêt commercial à documenter le sujet ; son verbatim technique est vérifiable sur la [documentation Perplexity](https://docs.perplexity.ai/docs/agent-api/migrate-from-sonar/overview) et sur son propre [GitHub](https://github.com/anomalyco/models.dev/pull/5137), mais son benchmark tarifaire (« about a third cheaper ») n'est pas indépendant. Deux, la variation exacte de comportement des presets `medium`, `high`, `xhigh` par rapport aux modèles Sonar Pro et Sonar Reasoning Pro qu'ils remplacent n'est pas publiée par Perplexity avec des metrics chiffrées ; le consultant qui audite un outil GEO tiers ne peut pas anticiper précisément la variation de résultats sans mesure empirique post-25 septembre. Trois, le mapping preset publié par Perplexity et repris par Byteiota est une correspondance suggérée, pas une équivalence garantie ; le comportement d'un preset `medium` sur une requête donnée peut différer significativement du comportement de `sonar-pro` sur la même requête. Quatre, la liste des outils GEO tiers concernés (Peec AI, Profound, tryprofound, Athena HQ, Scrunch, BrightEdge Copilot, Rankscale, Otterly, Xfunnel AI, Siftly, RankAI) est une reconstitution à partir de la connaissance des éditeurs qui exposent une intégration Perplexity dans leur documentation publique ; certains éditeurs peuvent utiliser une couche différente (Perplexity Search API dédiée, scraping direct, autres méthodes) et n'être pas concernés par cette migration. Cinq, la date du 27 septembre 2026 est confirmée par plusieurs sources indépendantes (Perplexity documentation directe, Perplexity community forum, LLM Gateway, Byteiota, UsagePricing, Ecorpit, AI Watch Station) mais la date effective d'exécution technique de la coupure pourrait être décalée de quelques heures selon le fuseau horaire (probablement Pacific Time côté Perplexity, à confirmer par l'éditeur).

## Brève 1 — Actualité SEO : Google étend AI Brief à sept nouvelles langues et publie un rapport unifié AI Max Search qui trace les termes de recherche déclencheurs, les créatifs affichés et les URL de destination sur une seule vue

Le 23 septembre 2026, Google a publié sur son [blog produit ads](https://blog.google/products/ads-commerce/ai-max-language-reporting-features/) l'annonce simultanée de deux évolutions des campagnes AI Max Search. Un, l'extension du closed beta d'AI Brief à sept langues supplémentaires : néerlandais, français, allemand, italien, japonais, portugais, espagnol. AI Brief est la fonctionnalité qui permet à un annonceur de fournir un brief court à Google et laisser l'IA générer les créatifs adaptés à chaque requête. Deux, l'ajout d'un rapport unifié AI Max Search qui montre sur une seule vue « what search terms triggered your ads, which creative assets the user saw, and exactly where they landed on your website ». La double annonce a été reprise le même jour par [Search Engine Roundtable](https://www.seroundtable.com/google-ads-ai-max-reporting-countries-42144.html) et par [MediaPost](https://www.mediapost.com/publications/article/418214/google-adds-ai-max-reporting-new-gemini-models-e.html).

Le rapport unifié comble un déficit opérationnel documenté depuis la mise en beta d'AI Max en 2025 : les annonceurs manquaient d'un lien traçable entre le terme de recherche déclencheur, l'asset créatif servi et l'URL de destination, ce qui rendait le pilotage d'un compte AI Max opaque. La vue unifiée réintroduit la traçabilité mais reste une vue Google produite par Google, sans intégration native aux outils tiers de reporting PPC (SkAI, Marin, Optmyzr, Adthena, etc.). L'extension d'AI Brief à sept langues élargit le périmètre de test opérationnel : un annonceur qui gère des campagnes multi-marchés peut désormais tester la génération créative Google sur ses marchés européens et japonais sans se limiter à l'anglais. Le concept [`data-proprietaire`](../../wiki/concepts/data-proprietaire.md) reçoit ici un contre-exemple : la donnée de trace search-term → asset → landing URL est produite et détenue par Google, pas par l'annonceur, et son extraction vers un data warehouse tiers reste soumise aux limites de l'API Google Ads.

Deux réserves. Un, Google ne publie pas de chiffre sur la performance différentielle attendue du rapport unifié versus les vues fragmentées historiques ; la valeur opérationnelle sera mesurable après plusieurs semaines d'usage. Deux, l'extension AI Brief reste en closed beta, l'accès n'est pas ouvert à tous les annonceurs, et Google ne détaille pas les critères de sélection des comptes bénéficiaires. Le communiqué indique « We'll share additional details and availability later this year ».

## Brève 2 — Actualité SEO : Google met à jour la documentation Page Experience le 23 septembre 2026 pour intégrer les quatre métriques CrUX Ad Metrics publicité, sans en faire un signal de ranking officiel

Le 23 septembre 2026, Google a mis à jour la page [Understanding page experience in Google Search results](https://developers.google.com/search/docs/appearance/page-experience) pour ajouter, dans la section Page Experience Resources, les quatre métriques CrUX Ad Metrics publiées la semaine précédente. Les quatre métriques sont : Ad Count (nombre moyen de frames publicitaires visibles dans le viewport), Ad Density (part moyenne de la surface du viewport occupée par des frames publicitaires), Ad Weight CPU (charge computationnelle cumulée du chargement et de l'exécution des scripts publicitaires), Ad Weight Network (trafic réseau cumulé des scripts et assets publicitaires). Les mesures sont accessibles via CrUX Vis, CrUX API, CrUX History API et le panneau DevTools Ad, selon la [documentation Chrome for Developers](https://developer.chrome.com/blog/crux-ad-metrics). Le repérage vient de [Search Engine Land](https://searchengineland.com/crux-ad-metrics-added-to-the-page-experience-seo-documentation-490490) et de [Search Engine Roundtable](https://www.seroundtable.com/google-page-experience-crux-ad-metrics-42141.html) le 23 septembre 2026.

L'ajout à la documentation Page Experience ne vaut pas signal de ranking officiel : Google n'a pas dit que ces métriques sont utilisées pour classer les pages. La ligne est placée dans la section « Page Experience Resources » et pas dans la section des signaux mesurables. Le concept [`fully-meets`](../../wiki/concepts/fully-meets.md) documenté dans notre revue reçoit un contour opérationnel : un éditeur qui optimise l'expérience publicitaire de son site pour maximiser la note Fully Meets d'un Quality Rater dispose désormais de quatre indicateurs empiriques mesurables sur son propre panel Chrome, plutôt qu'une évaluation qualitative interne. Un consultant qui audite un site fortement monétisé par la publicité (média, comparateur, contenu généré à haute densité publicitaire) peut incorporer ces quatre métriques à son rapport et argumenter des optimisations sur base de mesures Chrome, indépendamment de tout signal de ranking Google.

Deux réserves. Un, Google ne dit pas si ces métriques deviendront un signal de ranking à moyen terme ; la trajectoire historique des Core Web Vitals suggère qu'un signal introduit initialement comme mesure devient parfois un signal de ranking après quelques mois, sans garantie que ce soit le cas ici. Deux, la mesure Ad Weight CPU et Ad Weight Network exige d'installer le CrUX Vis ou d'interroger l'API sur son propre panel, l'accès à ces mesures pour un site tiers (audit concurrent) n'est possible que si le site tiers est présent dans le panel public CrUX (top 25 millions de sites approximativement).
